# Emulating the baseband — claims and evidence (2026-10-04)

This is the evidence file for the article, not the article. Each quoted sentence is followed by what the
code, the ROM and the bench show. Read « VERIFIED » as « verified in the full system (the phone
registers, calls, speaks) » unless the bench says otherwise, in which case both verdicts are given.

The text below is the article as drafted (quoted blocks), followed, claim by claim, by what the
repositories, the ROM and the bench actually show on 2026-10-04. Each check is marked
**VERIFIED** (reproducible from code, ROM disassembly or a run), **CORRECTED** (the claim as written
is not what the code does; the corrected statement follows), or **OPEN** (not checked).
Sources: `c54x_exe` (this repository), `/opt/GSM/qosmo` (QEMU fork + C54x core, `hw/arm/calypso/`),
`/opt/GSM/osmocom-bb` (layer 1), `/opt/GSM/osmo-operator/pont` (bridge), `/opt/GSM/tests` (bench),
the public ROM dump `ftp://ftp.freecalypso.org/pub/GSM/Calypso/dsp-rom-3606-dump.txt` (PROM0 identical,
word for word, to the one used here), and the binutils `tic54x` disassembler built from the 2.21.1
sources.

## What "processor fidelity" means now

> Capturing at `0x3f8a` (what `tx_rom_publier` does) takes the coded bits *before* the modulator. The
> host still has to add the training sequence, synchronisation and tail bits, and redo A5 at the right
> frame number. That is ROM at about 80 %.

**VERIFIED (mechanism), CORRECTED (the number)** — `src/pont.c:555-600`: 114 data bits + hl/hu read
from `data[0x3f8a..0x3f91]`; the A5 stream the ROM XORed is read back from `data[0x3f9b..]` and
published so that the bridge can undo it and re-cipher (`pont/dsp/uplink.py:24-36`). « About 80 % » is
not a measurement; the only count available is the coverage table (per treatment: 6 ROM, 7 host,
1 mixed on 2026-10-03). Replace the percentage by that count or by a bit count.

> Capturing the TSP script (`0x3cbb..`, marker `0x1c0a` = TOGBR2, then 16 BULDATA words at 10 bits)
> takes the stream *the ABB would receive on silicon*, with training sequence, tails, I/Q inversion and
> A5 already applied. The host then only converts ABB words into 148 bits and places them at the right
> fn/tn. This capture point is valid for every burst type (NB, RACH, TCH), and it is the one that
> matches the goal: a single pipe, the ROM decides everything.

**VERIFIED in the ROM, and now reproduced in emulation (2026-10-04)** — static reading of PROM0:

- `0xb5b8` `stm #15547,ar2` (0x3cbb): the ROM builds a TSP script for the ABB there each frame
  (register writes requested through NDB words 0x8ed..0x8f7, `0xb5ba-0xb5e5`).
- `0xb6fd` (RACH) / `0xb70f` (NB): `st #7178,*ar2+` → 0x1c0a = TOGBR2 (page 0, reg 5) with data 0x70,
  then the burst through dispatcher code 39 (`data[0x43ae]` = 0xb77f → `fcall 0x859f` → emitter
  `0x85a2`) or code 40 (NB emitter `0x85c1`), then the power word `*(0x3fc9)`, then `st #18` (AUXAPC).
- Emitter `0x8605-0x868f`: a segment table driven by DP+0x49 (loads from the sync/TSC copy at 0x3dca,
  the data at 0x3f8a, the tail/guard words at 0x3dcd), a bit accumulator in B, and `sth a,*ar2+` at
  `0x8632` with the register bits added (`add #6,16,a` = BULDATA1, reg 3; TSP encoding
  `(data & 0x3ff) << 6 | reg << 1`, `abb/twl3025.c:156`). The emitted word is therefore
  `(10 data bits) << 6 | 0x06`.
- `0x85c1` (NB): `xor *ar4+` over the 8 words 0x3f8a..0x3f91 with 0x3f9b.. (A5 stream), then the 26-bit
  TSC copied from DROM 0xa0c9 + 2·tsc (the 8 TSCs are at DROM 0xa0c9..0xa0d8). `0x85a2` (RACH): the 41-bit
  sync copied from DROM 0xa0d9..0xa0db (`4b7f 99aa 3c00` = 0100101101111111100110011010101000111100 0).
  Tail/guard words DROM 0xa0dc..0xa0dd (`1fff ffff`).
- `0xb773`: `xorm #0xAA80` over the 16 words when bit 14 of `0x3f92` is set — the I/Q inversion flips
  every other data bit (mask 1010101010 in the 10 data bits).

Bench, `./dsp_tester rach` (new test, 2026-10-04): for five random RA values with BSIC 7, the 16 words
after 0x1c0a decode to 160 bits = `11111111` (ramp fill) + `00111010` (extended tail, 05.02 §5.2.7)
+ the 41-bit synchronisation sequence + the 36 coded bits + `000` + guard ones; the 36 coded bits are
identical to `gsm0503_rach_ext_encode(ra, bsic)` (5/5), and the ROM's own copy of them in
`data[0x3f8a..0x3f8c]` as well (5/5). Example, ra=0xd4:
`1111111100111010 01001011011111111001100110101010001111000 000011011110000101011001111010110011 000 1111…`.

**CORRECTED (« reachable without touching the core »)** — it was not. In emulation the emitter never
produced the 16 words before 2026-10-04, for two reasons in the C54x core (`qosmo`,
`l1-dsp/c54x_exec.c`):

1. `CMPR CC, ARx` (binutils `0xF4A8` mask `0xFCF8`, 78 sites in PROM0) was not implemented: `cmpr eq`
   fell into `unimpl` (a no-op, TC unchanged) and `cmpr lt/gt/neq` into `RPT #k`, the F6xx no-op and the
   F7xx block. The emitter's loop `0x8608 cmpr eq,ar2 ; 0x8609 rc tc` (AR0 = end of the 16 words) returned
   at once on a stale TC = 1 (probe: ST0 = 0x107b before and after the CMPR). Fixed; `CALYPSO_CMPR_ANCIEN=1`
   restores the old behaviour.
2. `LD src, ASM [, dst]` (`0xF482` mask `0xFCFF`) ignored the ASM shift (ST1[4:0], two's complement):
   the accumulator was never shifted and all 16 words came out as `0xff06` (probe: B unchanged across
   `0x8625 ld b,asm` with ASM = 10). Fixed; `CALYPSO_LDASM_ANCIEN=1` restores the old behaviour.

So the TSP script is the right capture point, but it only exists in emulation since these two fixes.
With them, the bench's `tx-sdcch` (normal bursts, ROM-coded SDCCH) still passes 24/24.

> What the RACH trace shows points the same way: the ROM does execute the RACH task (`0xb6fd`, then
> `0x85a2` on each attempt), writes its 36 coded bits to `0x3f8a`, and the transmitter fills in the
> script. The only obstacle is on the system side: `montant.c` clears `d_task_ra` by default
> (`MONTANT_EFFACE_TASK_RA=1`), so the ROM has never been allowed to do a real RACH. The bit
> differences seen against the host-side encoder settle nothing until that 05.03 implementation has
> been checked against `gsm0503_rach_ext_encode` on the bench, which is the next measurement.

**VERIFIED, and the measurement is done** — probe on the bench: `0xb6fd` and `0x85a2` on each of the
5 attempts; `data[0x3f8a..0x3f8c]` = the 36 coded bits (`0de1 59eb 3000` for ra=0xd4). The « bit
differences » were an error in a hand-written 05.03 encoder (the CRC-6 remainder is inverted,
`remainder=0x3f` in `gsm0503_rach_crc6`); against libosmocoding the ROM is exact, 5/5. The system-side
obstacle is as stated (`montant.c:1236-1245`); the second obstacle, the two core bugs above, is now
removed on the bench. What remains for the full system: publish the TSP burst from `pont.c`, let the
bridge send it at the ROM's frame, stop erasing `d_task_ra`.

## The hierarchy for what comes next

> Maximum fidelity, reachable without touching the core: make the TSP script the single source of all
> uplink bursts (RACH, SDCCH, TCH, SACCH, FACCH), and transmit at the ROM's frame number so that its
> A5 is the right one.

**CORRECTED (core)** — see above. **OPEN (A5 at the ROM's frame)** — the bridge's comment says the ROM
« chiffre à l'heure du DSP, pas au fn émis » (`pont/dsp/uplink.py:24`, `99-couverture.sh:137`); which
frame number the ROM uses for the uplink stream (`a_a5fn`, `d_fn`, or its own counter) has not been read
in the ROM, and whether « the ROM's frame » equals the air frame once the bridge sends immediately has
not been measured. To check before building on it.

> Fidelity that requires work on the core: the cases where the ROM computes wrongly or not at all
> (downlink SACCH/8 at 80 % FIRE failures, `B_BFI`, the bench's `nb` and `fb0/fb1` tests).

**VERIFIED (the list), and one number the article must state** — ISA conformance of the emulated core
(`./isa_test tools/isa_tests.txt`, the worked examples of SPRU172C): **of 230 examples, 150 pass,
58 fail and 22 cannot be assembled by the harness** (208 `T` records and 22 `S` records in
`tools/isa_tests.txt`; unchanged by the two fixes above; CMPR is among the « not assembled »). A quarter
of the manufacturer's examples fail. Every « the ROM does X » is conditional on the core executing the
instructions of that path correctly, and the two bugs of 2026-10-04 were found exactly that way. The
list of failing examples (`./isa_test tools/isa_tests.txt | grep ^FAIL`) is the most profitable work
queue of the project before any new pipe. Bench on 2026-10-04: `fb0`, `fb1`, `fbsb`, `nb` FAIL; `boot`,
`idle`, `checksum`, `fb-afc`, `sb`, `tx-sdcch`, `rach` PASS. `99-couverture.sh:130,133`: SACCH/8 FIRE KO,
B_BFI.

> The most distant fidelity: the vocoder in the ROM, which means modelling the audio path from the DSP
> to the ABB.

**OPEN** — plausible (the ROM delivers TI-format speech frames to `a_dd`, GAPK decodes them on the
host, `99-couverture.sh:141`); nothing measured.

> In other words, the DSP has stopped being an obstacle to work around and has become the reference:
> whenever the host still does something, it is either because it has not yet been given the ROM's
> pipe, or because the core still has a bug. Both are measurable, and that is what is being measured.

**VERIFIED as a description of the method** — the RACH case of 2026-10-04 is exactly that: a ROM pipe
not yet used (`d_task_ra` erased), and two core bugs found by following the ROM's own code to the
point where it writes the burst.

## Reproducing the new measurements

```
# ROM : disassembly of the emitter and of the TSP script builder
objdump -D -b binary -m tms320c54x --adjust-vma=0x7000 PROM0.bin | less     # 0xb5b8, 0xb6fd, 0xb70f, 0xb773,
                                                                             # 0x859f/0x85a2, 0x859c/0x85c1, 0x8605-0x868f
# DROM tables : 0xa0c9..0xa0d8 (8 TSC), 0xa0d9..0xa0db (RACH sync), 0xa0dc..0xa0dd (tail/guard)
# bench
make dsp_tester && ./dsp_tester rach tx-sdcch -v
CALYPSO_CMPR_ANCIEN=1 ./dsp_tester rach          # before the CMPR fix : no burst in the script
CALYPSO_LDASM_ANCIEN=1 ./dsp_tester rach         # before the LD src,ASM fix : 16 x 0xff06
```
